# 使用 Cursor AI 工作赋能成果报告

> Web 驱动研发｜Go 服务端、Hubx 微前端、设备 SDK 
> 汇报人：简清｜2026 年 7 月 17 日

Cursor AI 主要用于 Web 驱动相关研发，覆盖 Go 服务端、Hubx 微前端和鼠标 SDK 三部分工作。实际使用集中在代码阅读、重复代码编写、接口联调、测试补充、问题排查和文档整理等环节。

在使用过程中，AI 负责提供代码初稿、排查思路和信息整理；方案取舍、关键实现和最终验证仍由研发人员完成。对于设备协议、数据一致性、异步任务和部署配置等风险较高的内容，均需结合代码审查、测试结果和实际环境确认。

## 一、Go 服务端

Go 服务端包括 `hubx-api`、`hubx-migrate` 等 Go 服务，承担 Web 驱动平台的接口服务、数据迁移和后端基础能力。日常开发中持续处理模块边界、数据库访问、容器构建和部署流程等问题。

### 1.1 数据库模型与测试

数据库相关开发中，Cursor AI 可根据项目已有的目录结构、字段命名和 GORM 使用方式，协助生成实体模型、迁移脚本及部分 SQL 转换代码。对于字段较多、关联关系明确的表，这类工作能够减少重复编写和人工检查的时间。

PostgreSQL 相关业务逻辑需要覆盖正常流程、异常返回和边界条件。结合 Mock 机制，Cursor AI 可先补齐单元测试的基础结构和常见测试用例，再由开发人员补充业务特有场景。目前，核心业务逻辑的代码覆盖率已达到 80% 以上。

### 1.2 分层与架构维护

复杂业务开发时，会使用 Cursor AI 检查调用链和包依赖，重点关注业务层是否直接依赖 Controller、Repository 等不应依赖的模块，以及新增逻辑是否破坏原有分层约定。

这类检查不能替代代码评审，服务端的基础组件、业务逻辑和数据访问层因此保持相对清晰的边界。

### 1.3 构建与发布排查

在 Docker 镜像构建、发布失败或运行环境异常时，Cursor AI 可协助分析 Dockerfile、多阶段构建、镜像层和 Go 二进制文件大小。

例如，针对服务镜像偏大的问题，可根据构建产物判断体积主要来自 `hubx-api`、`hubx-migrate` 等二进制文件，再评估移除调试信息、精简构建参数或拆分迁移程序镜像等处理方式。发布问题的排查范围能够更快收敛，后续仍需在 CI/CD 和实际部署环境中完成验证。

### 1.4 工作成果

服务端重构、基础组件调整和故障定位更快，能够把更多时间放在业务规则、异常处理和稳定性上。异步任务、事件处理、服务扩展和可观测性相关能力也有了较明确的接入位置。

## 二、Hubx 微前端项目

Hubx 面向 Web 驱动场景，包含主应用、鼠标子应用等模块。微前端架构用于承载不同业务页面和设备能力，使各模块可以独立开发、部署和迭代，同时在统一入口下完成集成。

### 2.1 代码理解与模块接入

维护既有模块或接入新功能时，Cursor AI 可用于快速阅读目录结构、追踪调用关系和确认依赖来源。跨应用接口调用、路由衔接、公共组件引用和状态传递等问题，通常需要先理解已有实现，再确定改动范围。

对于代码量较大、历史改动较多的模块，AI 可以帮助定位相关文件和调用入口，减少手工检索时间。实际改动仍需结合主应用和子应用的运行行为进行联调。

### 2.2 架构调整与文档维护

Hubx 的迭代过程中，部分模块会出现职责交叉、重复逻辑或公共能力分散的情况。Cursor AI 可辅助检查相似实现和模块间引用，作为重构前的参考信息。

技术说明、接口文档、迁移记录和代码注释也会使用 AI 整理初稿。文档完成后需根据当前代码、接口定义和发布流程逐项校对，避免说明与实际实现不一致。

### 2.3 工作成果

Hubx 为 Web 驱动业务提供了相对独立的模块开发方式。新增功能通常只需在对应子应用或公共模块中完成开发，减少对其他业务模块的直接影响。

服务端、前端应用和设备能力围绕统一的平台协作，项目接入和版本发布的边界更清楚。对于需要跨团队配合的功能，也能更早明确接口、依赖和验证责任。

## 三、SDK（原相、通用新协议等）

SDK 覆盖原相、通用新协议等设备能力，负责向前端应用和业务页面提供统一的调用接口。业务页面可基于 SDK 完成设备控制、状态读取和功能适配，避免在多个页面中重复处理底层协议和设备差异。

围绕 Web 驱动业务，推进 SDK 的交付、复用与版本化管理，使设备能力能够以更标准化的方式接入前端应用和业务页面。相关工作服务于键盘鼠标类产品的 Web 研发与驱动管理场景。

### 3.1 协议适配与接口开发

协议适配工作涉及字段定义、命令参数、设备能力差异及调用时序。Cursor AI 可协助检索协议相关代码、分析已有调用链，并对不同设备实现进行对比。

类型定义、接口封装、参数校验、错误处理和使用示例等重复性内容，可以先由 AI 生成初稿。涉及真实设备行为的部分，必须连接设备进行调试，确认返回值、异常场景和兼容性后才能合入代码。

### 3.2 版本管理

在 SDK 的 Monorepo 管理和版本发布中，AI 也可用于检查依赖关系、整理变更内容和生成发布说明，减少多个项目引用同一设备能力时的维护压力。

配合 Web 驱动管理平台，部分原本需要研发修改代码才能完成的设备接入工作，已逐步转为可配置流程。测试人员可以自行完成设备接入，研发则将更多时间投入 SDK 能力完善和复杂问题处理。

### 3.3 工作成果

设备能力接入的接口更加统一，业务页面不需要反复处理底层设备差异。测试人员可以在平台上自行完成设备接入，减少等待研发修改代码的环节，研发可以集中处理协议适配和复杂问题。

## 四、AI 使用原则

Cursor AI 用于辅助代码阅读、编写、测试和问题排查，方案取舍、关键代码修改和正式交付仍由研发人员负责确认。 

- 开发前先确认业务目标、接口约束、数据模型和现有项目结构，避免脱离上下文直接生成代码。
- AI 生成的代码需符合项目规范，并完成编译、单元测试、代码审查和环境验证后再合入。 
- 涉及设备协议、数据一致性、异步任务、部署配置和安全边界的改动，需结合实际运行情况进行人工验证。
- 将可复用的代码模式、测试场景、排障记录和技术文档整理沉淀，减少后续重复处理。
